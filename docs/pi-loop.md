# Piの同じセッションで作業を定期継続する

`~/.pi/agent/extensions/loop.ts`が`/loop`を追加します。新しいプロセスやOSタイマーを作らず、現在のPiが完全に待機状態になってから次の巡回を予約します。既存の投稿タイマーや権限ゲートは変更しません。

## 開始・確認・停止

新規導入後はPi画面で`/reload`を実行してください。その後は次のコマンドを使えます。

```text
/loop start 10m 承認済みの作業を継続する。必要な手順書をreadで読み、成果物と検証結果を残す。
/loop status
/loop stop
```

開始すると最初の巡回がすぐに動きます。次の巡回は処理完了から10分後です。実行中・未処理の入力あり・圧縮中には巡回を重ねません。間隔は正の整数と`s`、`m`、`h`で指定します。省略時は10分です。10分は起動間隔の初期値で、利用枠・費用に基づく最適値ではありません。

巡回は拡張由来のcustom messageです。本人の新しい承認として偽装しません。LLM用の`loop_control`は状態確認と停止だけを提供し、開始はできません。既存のツールと権限ゲートを通して作業し、モデル・effort・課金経路は変えません。

## 中断時は自動再開しない

承認画面、ツールの失敗・拒否、モデル応答のエラー・中断・出力上限、セッション終了・再読込・分岐変更、モデル・effortの変更で停止します。モデル応答のエラーでは現在のrunもabortし、Pi本体のretry待ちも中断します。ツールの失敗時は次の巡回を止め、現在のrunによる結果整理は妨げません。再開には明示的な`/loop start`が必要です。

Piを終了したりPCがスリープしたりすると巡回は実行できません。スリープや既存の資源制限を解除する機能ではありません。別のPiでの制作や既存ジョブとの排他は、対象リポジトリの手順とロックに従います。

## 初回だけ現在のセッションに開始依頼を渡せる

インストール中のPiは未読込の拡張を自分で呼べません。本人が追加と開始を依頼した場合だけ、`~/.local/state/pi-loop/<session-id>.json`に一度限りの開始依頼を保存できます。これは設定の正本ではなく、実行時の引き継ぎ状態です。

拡張は`session_start(reason=reload)`のときだけ、そのセッションIDに対応するファイルを読みます。version、セッションID、cwd、モデル・effort、間隔、タスクが一致・妥当な場合に限り、依頼を削除してから開始します。通常起動、resume、forkでは消費せず、別プロジェクト・別モデルでは開始しません。再読込の成功だけでは巡回の完了を意味しません。

## ソースと検証

- ソース：`home/dot_pi/agent/extensions/loop.ts`
- 反映先：`~/.pi/agent/extensions/loop.ts`（Pi全体と同様、`home/.chezmoiignore`でam5-itxだけ）
- テスト：`python3 -B tests/pi-loop.py`。仮のPi・時計・HOMEと、モデル呼び出しなしの実Pi RPCで確認します。

対象指定の`chezmoi diff`、`chezmoi apply --dry-run --verbose`を確認してから、このファイルだけを反映します。ゲート・フック・権限設定の変更は含めません。
