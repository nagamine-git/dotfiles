# 仕事の置き場所と流れ

EFG technologies (一人法人) で、人 (永峰) と AI エージェント (Claude Code / Codex) が同じ決まりで動くための表。
要点は `dot_agents/AGENTS.md` の「仕事の置き場所」にあり、全エージェントが読む。2026-10-21 決定。

## 何をどこに置くか

| もの | 置き場所 | 決まり |
|---|---|---|
| 会社のタスク | Linear (チーム EFG) | 正本はここだけ。Slack・Artifact・会話で決まったことも Linear に戻す |
| 本人にしかできない作業 | Linear: 担当 永峰、状態 In Review | 大きさでなく「人にしかできないか」で決める (権限・お金・ログイン・鍵・事業の判断)。本文は「決めること / 手順 (何分) / 終わった合図」 |
| 本人への連絡 | Slack bot «Claude (EFG)» の DM (`slack-claude dm`) | 1 日 1 回まとめて送る。作業が止まっているものだけすぐ送る |
| コードの変更 | GitHub の PR | 下の段分けに従ってマージ・デプロイ |
| KPI・滞留 | Tailscale 上の PWA ダッシュボード 1 つ | 滞留は Linear の画面で見る。ダッシュボードを増やさない |
| 一時的な確認 (比較・見本・報告) | Artifact | 残すべき結論は Linear か repo に移す |
| 個人のタスク | 野帳 (今日の分) / Google カレンダー (日付・繰り返し) | Linear に入れない |
| 個人の定期作業を AI に任せる | クラウドの定期実行、手元が要るなら am5-itx の timer で `claude -p` | お金の移動は AI がしない。人の作業は bot の DM で知らせる |

## Linear の仕分け

2026-10-22 整理。担当者は責任の所在であり、永峰担当の課題すべてを本人の手作業とは扱わない。

| 状態 | 意味 | AI が行うこと |
|---|---|---|
| Triage | 扱うべきか未整理の依頼・提案 | 既存課題と照合し、採用・重複統合・却下・再確認へ仕分ける。曖昧な事業判断は本人へ出す |
| Backlog | 残すと決めたが、まだ着手しない | 次の行動・前提・必要なときの確認日を残す |
| Todo | 次に着手する仕事 | 必要な前提がそろっているか確かめる |
| In Progress | 実際に進めている仕事 | 調査・実装・別エージェントのレビュー・検証を進める |
| In Review | 本人の具体的な判断・操作待ち | 本人が行うこと、理由、所要時間の目安、完了の合図を提示する |
| Done | 受入条件を確認できた | 成果物・検証の証拠・残る制約を記録する |

明確な実行指示は Triage で止めない。本人の判断が不要な AI 作業を In Review に置かない。完了・キャンセル・重複は意味が異なるため、古いという理由だけで入れ替えない。
他のセッションが進めている課題は、担当・コメント・PR の状態を確認し、並行して実装しない。

### 見る画面

新たなタスク管理を増やさず、次の条件を保存ビューとして使う。保存ビューの作成・変更後は条件と一致する課題を読み戻して確認する。

| ビュー | 条件 | 表示 |
|---|---|---|
| 本人待ち | EFG、未完了、担当 永峰、状態 In Review | 優先度順。Slack bot の本人依頼と PWA の件数も同じ条件にする |
| 今週進める | EFG、現在の Cycle、状態 Todo または In Progress | プロジェクト別。本人待ち・完了・未着手候補を混ぜない |
| 期限間近の定期作業 | EFG、未完了、ラベル 運用、期限が過去または今後30日以内 | 期限順。来年以降の予定は出さない |

### 優先度・Cycle・依存関係

- 優先度は進行中・次に着手・他の作業を止める課題を中心に付ける。緊急は事故・漏えい・実際の期限などの根拠がある場合に限り、全件を高優先度にしない。
- 今週の Cycle には今週進める対象を選ぶ。将来の定期作業を自動的に入れず、期日を過ぎても未実施なら完了にはしない。
- 観測待ち・外部待ちは、次に確認する日時または条件を本文に残す。更新が古いことだけで実験の失敗や不要な仕事と判断しない。
- 前提は本文だけでなく blockedBy / blocks でつなぐ。前提が未完了でも進められる設計・テストを分け、受入確認まで済んだとは扱わない。

### 課題の書式

本人依頼は次の形にそろえる。所要時間は目安であり、ポイント見積りを本人へ依頼する条件にはしない。

```text
## 決めること
判断が要る内容。作業だけなら「なし」。

## 手順（目安○分）
どの画面・端末で何をするか。必要なURL、推奨案と理由。
鍵の値は書かず、Agents vault の登録先と必要な権限を示す。

## 終わった合図
本人の操作と、その後AIが行う確認。
```

AI の実行課題は「目的 / 範囲と前提 / 受入条件 / 検証と証拠」を書く。該当する既存の開発テンプレートを優先し、同じ仕事を別の課題として増やさない。
Slack は通知と入口に限定し、やり取りで決まったことを Linear に戻す。bot が使えない間は本人待ちを Linear に残し、DM を送れたとは報告しない。

## PR の段分け

| 段 | 対象 | マージ・デプロイ |
|---|---|---|
| 自動 | ドキュメント、テスト、依存のパッチ・マイナー更新、見た目の修正、lint | CI が緑なら自動マージ・自動デプロイ |
| 本人承認 | 課金、認証・権限、データの移行・削除、鍵、本番の設定、外部への送信、費用が増える変更 | レビュー観点を固め、エージェントが指摘を解消してから本人が承認する |

迷ったら本人承認の段に置く。

2026-10-22 決定: 「PR は本人が先にレビューする」という一律の義務は廃止する。実装担当とは別のエージェントがレビューし、指摘の解消と対象コミットの CI 成功を確認してから、上の段分けに従って進める。
本人承認の段で求めるのは、変更の目的・影響・リスク・戻し方を踏まえた承認であり、本人が最初にコードを通読することではない。
学習のために本人がレビューする場合も任意とし、通常の PR を待たせる前提にしない。

### GitHub と Linear の状態連携

- PR の本文に Linear の課題をリンクする。エージェントのコードレビュー中は In Progress のままとし、In Review は本人の承認が必要な場合に限る。
- PR の作成・レビュー・マージ可能の通知で、本人依頼の課題を自動的に In Review にしない。鍵の登録などの本人依頼は、実装課題と分けて関連付ける。
- 本番確認が必要な課題を、マージ時点で自動的に Done にする設定は使わない。マージ後も In Progress とし、デプロイ・動作確認を証拠とともに記録してからエージェントが Done にする。
- ドキュメントだけなど、マージで受入条件をすべて満たす場合は、別エージェントのレビューと対象コミットの CI 成功を確認して完了にしてよい。
- 自動マージの可否は変更の実際の影響で判断する。パスや PR のラベルだけで認証・課金・データ削除などの変更を低リスクと扱わず、GitHub の保護・承認要件を回避しない。

参照: [Triage](https://linear.app/docs/triage)、[保存ビュー](https://linear.app/docs/custom-views)、[Cycles](https://linear.app/docs/use-cycles)、[GitHub連携](https://linear.app/docs/github)。有料の自動仕分け・新しい鍵・新しい通知先は、この運用整理のために追加しない。
